# The public API

This page is for a developer who depends on the SDK packages and wants to know what they can rely on, and for a contributor who changes them. By the end you will know what counts as public across the six packages (`@mapcairn/core`, `@mapcairn/map`, `@mapcairn/react`, `@mapcairn/theme`, the MapLibre adapter `@mapcairn/adapter-maplibre` and the umbrella `@mapcairn/sdk` that re-exports them), how a change to it is found in review, and how a change is classed for a release. The first four have been public since the `0.1.0-rc.1` release candidate (`docs/plans/0014-sdk-release.md`) and the adapter and the umbrella join them in `0.1.0-rc.3` (`docs/plans/0016-adapter-maplibre-package.md`, `docs/plans/0015-sdk-umbrella-package.md`); this guide is the rule the release scripts and reviewers use.

Checked against `@mapcairn/sdk` %sdkVersion%, the version in this repository.

### Custom properties are not public; `data-*` style hooks are undecided

The maintainer has decided that the build-hashed custom property names (the token names in `tokens.css`, such as `--rogqo0r`) are **not public API**. They are private and may change in any release, so a host must not write a stylesheet against them, and a change to them is never a breaking change. Theming will go through a generated stylesheet, not through these names.

`data-testid` values are not public either (above). Whether the other `data-*` attributes the components set, which `styles.css` selects on, are public is still open: it is the maintainer's decision, listed among the open release decisions in #423. Until it is made, treat them as not public: a host should not write a stylesheet or a test against them, and a change to them is not a breaking change.

## The umbrella package

`@mapcairn/sdk` re-exports the other five packages, so an app installs one name and imports from one place. Its entry points are `.` (every export of `core`, `map`, `react` and `theme` in one flat list), `./core`, `./core/contracts`, `./map`, `./react`, `./theme` and `./adapter-maplibre` (each the same as the package of that name), and `./styles.css` (the three stylesheets: tokens, then the map's, then the engine's). The adapter is at its subpath only: the root never imports it or `maplibre-gl`, so an app that does not import the subpath has no map engine in its page or its server bundle. `maplibre-gl` (`^6.18.0`) is a required peer of the umbrella, because the subpath needs it. The rules that hold it to the packages:

- **Same types, same values.** Every entry is `export * from` the package and nothing is copied, so a type from the umbrella is the package's own. A new export of a package reaches the umbrella's root with no edit, and its change shows in the package's API report. The umbrella's own report (`packages/sdk/api`) lists only the star re-exports and the two tie-breaks, because API Extractor does not expand a star re-export of another package.
- **Tie-breaks.** Two names are declared by more than one package: `ScaleBar` (the component from `map`; `core`'s measurement type stays at `@mapcairn/sdk/core`) and `ReadingDirection` (from `core`; `react` declares the same type again). A new collision fails `tsc` until the umbrella settles it, and a test compares the collisions in the reports with the tie-breaks. The package the root already exports keeps its binding, so changing which package wins a tie-break is a breaking change for the umbrella.
- **No test code at the root.** The contract suites are reachable only at `@mapcairn/sdk/core/contracts`, which carries `core`'s optional `vitest` peer.
- **One version.** The six packages share one version, and the umbrella depends on the other five at that exact version. An app that also lists one of them itself must keep it at the umbrella's version, or it gets two copies and two React contexts, so a provider from one copy is invisible to a component from the other.
- **Declaration merging.** A host that adds a service of its own augments `@mapcairn/core` (`declare module "@mapcairn/core"`) and lists `@mapcairn/core` as a dependency at the umbrella's version; `Services` read through the umbrella then holds the new service. Augmenting `@mapcairn/sdk` also merges today, and the consumer check covers it, but the supported form is to augment `core`.

## What a tarball holds

`npm run pack:check` (`scripts/release/packCheck.mjs`) packs each SDK package with `npm pack --dry-run --json` and fails when a tarball holds anything but:

- `package.json`, `README.md` and `LICENSE`;
- files under `dist` ending in `.js`, `.js.map`, `.d.ts` or `.css`, which is all a build writes.

So no source (`src` is not in `files`; each `.js.map` carries its source in `sourcesContent`, so a debugger still shows it), no test or snapshot, no dotfile (such as `.env` or the `.built` stamp), and no data file, image, font or tile archive. It also fails when a file that `exports` or `types` names is missing from the tarball (the `@mapcairn/source` condition is left out, because it names a file only this repository has), when `files`, `publishConfig` or a `main` field differs from what the SDK manifests have, and when a tarball is over its size ceiling (`SIZE_CEILINGS` in the script, about one and a half times the size measured when it was set; raising one is an edit in a pull request). It also fails when `package.json`, `README.md` or `LICENSE` is missing, when `license` is not `AGPL-3.0-only`, when the fields the npm page shows are missing or wrong (`repository` with the package's own `directory`, `homepage`, `bugs`, `keywords` and `description`), and on a source map whose `sourceRoot` or a `sources` entry is absolute, a URL, or resolves outside the package's `src`. A script under `dist` must have a source map naming files that exist in `src`, except an entry point (named by `exports`) and the bundler's helper under `dist/_virtual`, and a declaration or stylesheet must be one an export names, so a stray file such as `dist/secret.js` fails. The check reads what is on disk, so the release `verify` job must run it after `npm run build:sdk -- --force` from a clean checkout, which empties `dist` first. It works on a private package, since `npm pack` does.

`npm run consumer:check` (`scripts/release/consumerCheck.mjs`) packs the six packages into a temporary folder outside the repository and installs them into a fresh app there, with the repository's `.npmrc` (so the three-day minimum release age holds) and the versions of its seven tools (`react`, `react-dom`, `vite`, `typescript`, the two `@types` packages and `maplibre-gl`, the adapter's required peer, which a strict pnpm install refuses to leave out) read from the root lockfile; the packages' own dependencies resolve fresh from the registry within the three-day age. It installs with npm, with `--legacy-peer-deps` and, when one is already installed, with pnpm set to strict peer dependencies, and renders `MapChrome` in plain Node. In the npm install it then runs `tsc` under `bundler`, `node16` and `nodenext` resolution, builds with plain Vite (no plugins) that imports `@mapcairn/theme/tokens.css`, `@mapcairn/map/styles.css` and `@mapcairn/adapter-maplibre/styles.css`, and renders the built server bundle. It also builds the app as a Worker with plain Vite, resolving with the `workerd`, `worker` and `browser` conditions, and runs that bundle on workerd (the Workers runtime the host is published on) through Miniflare, which the root `package.json` declares as a devDependency pinned to one exact version (it is a prerelease), so the leg does not depend on the Cloudflare Vite plugin's copy being hoisted. Those conditions choose the third-party builds a Worker takes, such as React's stream renderer; the packages' own exports have only the `@mapcairn/source`, `types` and `default` conditions, so what the leg shows is that their `default` build runs on Workers. The Worker reports its runtime name, so a render in Node cannot pass for it. workerd runs in a child process with a timeout that stops it on an interrupt, listens on 127.0.0.1 only (set explicitly) and sets no compatibility flag, so the packages need nothing beyond the plain Workers runtime. The Yarn leg installs the tarballs with Yarn Berry (the `node-modules` linker, no scripts, a seven-day minimum age) at the one exact version `YARN_VERSION` in `scripts/release/consumerLegs.mjs`, pinned in the app's `packageManager` with the sha512 digest corepack computes for that release (taken from a download into an empty corepack home, and checked there against a wrong digest, which corepack refuses) and fetched through corepack into its cache, which every project on the machine shares, then renders in plain Node and builds with plain Vite. The Bun leg installs with Bun (1.3 or later, the first to read the seven-day minimum release age; an older Bun fails the leg) and renders with it. It has never run: Bun was not available where it was written, so treat it as untested until someone runs it. It needs a network.

The umbrella app also draws a real map in a browser (`scripts/release/consumer-browser/`, `browserRun.mjs`). Its manifest names only `@mapcairn/sdk` among the MapCairn packages, with the peers `react`, `react-dom` and `maplibre-gl`. The page imports the interface from `@mapcairn/sdk`, `createMapLibreMapAdapter` from `@mapcairn/sdk/adapter-maplibre` and the stylesheet from `@mapcairn/sdk/styles.css`, takes the worker file's URL from Vite's `?worker&url` import for `loadWorkerUrl`, and gives the adapter a basemap only when a button is pressed. The leg builds it with plain Vite, serves the build from a static server on 127.0.0.1 under the policy that `buildContentSecurityPolicy` in `examples/embed` builds for one basemap (a unit test keeps the two equal: nothing inline, `worker-src 'self' blob:`, `connect-src` limited to one made-up style origin), and drives it with the repository's Playwright Chromium. The style document is answered from the browser's routes and every other origin is refused. It passes when no request for the style, the engine or the worker was made before the button was pressed, the engine's worker came from the page's own origin, no request went anywhere but that origin and the style, the style loaded and the map drew a frame whose pixel in the map region is the style's background colour, the engine container has the map background token and no engine control shows, and the page reported no Content-Security-Policy violation, console error or uncaught error. It runs on packed tarballs; it is also wired into the published-version check (`release:verify-published`), which has not run it yet because no published version has the `adapter-maplibre` subpath. It proves plain Vite with one app and Chromium on one machine, not other bundlers or browsers.

The same app also builds the README's own quickstart (`quickstartRun.mjs`): the README's page, style sheet and `main.tsx` as written, served under the README's policy line with the default basemap's real style document and local stand-ins for its tile set, tiles, sprite and glyphs, so it makes no network request. It fails on any violation or console error, and runs again with `connect-src`'s origin and `worker-src`'s `'self'` taken out, each of which must raise one.

Where the browser leg runs: on a developer's machine it skips with a warning when Playwright or its Chromium is missing (`npm run playwright:install -w @mapcairn/web` installs it). On GitHub Actions it fails when Playwright is installed and Chromium is not, and the CI `SDK packages` job installs Chromium for it. That job is a required check on `main`, but the release workflow's `check` job installs nothing, so Playwright is missing there and the leg skips with a warning: a release run does not draw a real map. The `release` skill therefore makes `npm run consumer:check`, run with Chromium, a go/no-go item before a Release pull request opens.

Some legs skip with a warning annotation on GitHub Actions when their tool is missing: pnpm (which is not installed for the check), Yarn when corepack is missing or cannot download Yarn (Node 25 and later ship no corepack), Bun only when `bun` is not on the path (any other Bun failure fails the check), workerd when Miniflare is not installed, which is the case in a job that runs no `npm ci`, and the browser leg when Playwright is not installed. Nothing is installed for a skipped leg. The CI `SDK packages` job installs the repository's dependencies, so it runs the Yarn and workerd legs and skips Bun: installing Bun there would need a setup action that has not been pinned and reviewed. A job with no install, such as the release workflow's `check` job, skips the workerd leg; run `npm run consumer:check` on a machine that has Bun to cover Bun. The Yarn and Bun legs do not run against already published packages (`release:verify-published`), because their seven-day release age would refuse a release made today; they do run on packed tarballs, whether packed here or given with `--tarballs`, which are `file:` installs. The release workflow's `check` job runs the check on its tarballs with no `npm ci`, so there it runs the Yarn leg, skips workerd with a warning (no Miniflare) and skips Bun. Yarn Plug'n'Play is not checked: the check has not tried it, and Vite and Node would need Plug'n'Play-specific setup for it.

The same check then repeats the render, the three `tsc` runs, the plain Vite build with its stylesheet checks, the server bundle and the workerd leg for an app that lists only `@mapcairn/sdk`: its source imports the umbrella alone (`umbrellaSource` rewrites the fixture's imports, the stylesheet imports become `@mapcairn/sdk/styles.css`, and the fixture's declaration merging augments `@mapcairn/sdk`), so the other packages reach it only through the umbrella (the adapter at `@mapcairn/sdk/adapter-maplibre`, which all three `tsc` runs resolve), and it installs with pnpm set to strict peer dependencies, where nothing but the umbrella and the engine is reachable from the app. That app also proves that the umbrella's root holds no map engine, from the module graphs of five Vite builds (`bundleGraph.mjs`): the client, server and Worker bundles built through the root never reach `maplibre-gl` or the adapter, and two control builds of a file that imports the adapter through the subpath do, so a detector that sees nothing is caught. A third app lists the umbrella with `core`, `map` and the adapter at the same version and must install one copy of each (no SDK package has a nested `node_modules`, the umbrella's `MapChrome` is the object `@mapcairn/map` exports, and the adapter's factory is the same function at both names), render with the umbrella's providers around the component from `map`, and read a service merged into `core` through the umbrella's `Services`. The Yarn, Bun, `--legacy-peer-deps` and published-package notes above apply to the first app only, and the published-package run repeats the umbrella-only and mixed legs with npm.

`map` lists `@vanilla-extract/css` in `dependencies` although nothing loads it at run time: `@vanilla-extract/recipes` names it as a peer, and a strict pnpm install (`strictPeerDependencies`, no automatic peers) refuses a missing one. The maintainer decided on 2026-11-20 to declare it as a dependency (about a dozen small permissively licensed packages) and not as a peer, which would put it on every consumer. Remove it if `recipes` drops the peer.

CI runs both in the `SDK packages` job, which is a required check on `main`, and the weekly Repeatable build compares the `dist` folders and the tarballs of two clean builds.

The package READMEs are written for the npm page, which shows each one away from the repository. They install the package with npm, pnpm and yarn side by side, hold one **Status** line that says what a `0.x` version promises (the text is in [[`docs/guides/releasing.md`](https://github.com/MapCairn/mapcairn/blob/main/docs/guides/releasing.md)](https://github.com/MapCairn/mapcairn/blob/main/docs/guides/releasing.md), "The first release", step 4), and link to the repository only by absolute URL, because a relative link means nothing on npm. `packages/core/src/lint/packageReadmes.test.ts` checks this, and that the code in them imports only what `examples/embed` imports. The `repository.url` is `git+https://github.com/MapCairn/mapcairn.git`: npm's trusted publishing requires it to match the GitHub repository exactly, so a fork that publishes must change it.

## The report of the exports

Each entry point has a report, generated by API Extractor from its built declarations, at `packages/<name>/api/<entry>.api.md`:

- `packages/core/api/index.api.md` and `packages/core/api/contracts.api.md`
- `packages/map/api/index.api.md`
- `packages/react/api/index.api.md`
- `packages/theme/api/index.api.md`
- `packages/adapter-maplibre/api/index.api.md`
- `packages/sdk/api/<entry>.api.md`, one for each entry point of the umbrella (`index`, `core`, `coreContracts`, `map`, `adapterMaplibre`, `react`, `theme`)

The report lists every exported name with its signature, so a change to the public API shows as a diff in the pull request. The reports are generated, never written by hand.

- `npm run api:check` builds the SDK if it is stale, regenerates the reports and fails when one differs from the committed file, is missing, or has no entry point, printing the changed lines (at most 40). The CI step that runs it after the build is the gate. `packages/core/src/lint/apiReports.test.ts` also compares the reports during `npm test`, so a local test run finds the same failure, but it is not the gate and a skipped test run does not skip the check.
- `npm run api:update` regenerates and writes them. Run it after a change to an exported name, read the diff, and commit it with the change.
- Read the diff of a report as a reviewer would. A new line is a new export; check it was meant to be public. A removed or changed line is a breaking change, unless the member was never part of what a host used.
- A `// Warning: (ae-forgotten-export)` line means an exported declaration names a type the entry point does not export. A host can use the type but cannot import it by name. Export the type, or stop exposing it.

### Release tags

The maintainer has adopted this tag policy. Without a tag, every export in a report is public. The tags mean:

- `@public` (the default, so it is not written): covered by the rules on this page.
- `@beta`: exported so a host can try it; named in the release notes. Under `0.x` a minor release may break anything, so `@beta` is advisory until `1.0.0`. A host should not depend on a `@beta` export in a library of its own.
- `@internal`: in the entry point only because a barrel (`export *`) or another SDK package reaches it, and not supported: a tuning constant, an engine layer id or a helper that turns the SDK's data into engine input. An export that gains `@internal` is a likely breaking change (a host may use it today); one that is `@internal` from the start never breaks anyone. A name used only inside one package and its own file is not exported at all.

Without a tag an export is public. A light sweep of the four packages before `0.1.0` (see the export audit issue) hid the names that nothing outside their own file used and tagged the clearly internal ones `@internal`: pixel and timing constants, engine layer ids, and the helpers that build engine input in `map`. It is not an export-by-export audit: anything plausibly part of the supported surface stays public and untagged, and the rest of the review happens as the API evolves under the report check. A new tag appears in the report diff, which is how a reviewer sees that an export was narrowed. A name that a guide or a host's tests use stays public even when a sibling is tagged `@internal` (for example `MIN_SUGGEST_LENGTH` is public while `MIN_SEARCH_LENGTH` is `@internal`).

One `ae-forgotten-export` warning remains, in `core`: `MessageParams` names the unexported `MessageParamOverrides`. It does not stop a host from calling the API.

The `contracts` entry point shares its types with the main entry. Its declarations import every type the main entry exports from `@mapcairn/core`, so a host that names a type from both entries gets one declaration, and the `contracts` report has no forgotten export. `scripts/shareDeclarations.mjs` does this while the package builds (`ARCHITECTURE.md`, "Building the SDK packages"), and a test in `packages/core/src/lint/sdkDist.test.ts` fails if `contracts.d.ts` declares a name that `index.d.ts` declares. A name only `contracts` uses stays declared there and must be exported or not exposed.

### What produces the reports

The reports come from API Extractor, which reads the declarations with its own bundled TypeScript, while the build emits them with the repository's TypeScript 7. API Extractor's bundled TypeScript also reads the declarations in `scripts/shareDeclarations.mjs`, so a bump of it can change the built `contracts.d.ts` as well as the reports. A new version of either can change every report, and the weekly dependency pull request that bumps them fails `api:check`. On that branch run `npm run api:update`, read the diff to see whether the change is real, and commit it. `.github/dependabot.yml` groups the two apart from the other npm updates, so this happens in one small pull request.

### TSDoc warnings

The same run prints warnings, and never fails on them:

- `ae-undocumented`: an export, or a member of an exported type, with no TSDoc comment.
- `ae-unresolved-link`: a `{@link}` that names something that is not exported.
- `tsdoc-*`: TSDoc syntax that API Extractor cannot read, such as an unescaped `}` or a `@param` with no hyphen.

CI prints each warning in a group and a count for each package as one annotation. The counts are not a baseline and nothing compares them with a limit. Whether to ratchet them is the maintainer's decision. `npm run api:check -- --verbose` lists every warning.

## Decisions on record

- **Tags.** The release tag policy above is adopted as written.
- **Export audit.** The maintainer decided on 2026-11-20 on a light sweep of the public exports before `0.1.0`, not a full audit (see the export audit issue). The first pass is described under Release tags.
- **Not public.** `data-testid` values (for the project's own tests, may change) and `peerDependencies` ranges (may change in a minor release while on `0.x`). The `data-*` hooks that `styles.css` selects on stay undecided.
- **Branch up to date.** Turning on the ruleset's "require branches to be up to date" is a maintainer step for later, once the release work settles. It is nothing for an agent to do; until then, two pull requests that both change a report can turn `build` red on `main` when the second merges.

- **Tool.** API Extractor produces the reports and the declaration rollup. TypeDoc is not used.
- **Published shape.** ESM only, with no `main` field. TypeScript resolves the packages with `node16`, `nodenext` or `bundler` resolution only, not `node10`.
- **Custom properties.** Not public (above).
- **Audit finding on `minimatch`.** `npm audit` reports a `minimatch` finding through `@microsoft/api-extractor`. It is accepted, with this record: API Extractor runs only at development and build time, never in a package a host installs, and the glob patterns it matches come from this repository's own build configuration, not from outside input. Drop the acceptance when API Extractor moves to `minimatch` 11 or later.

## How a change is classed for a release

`npm run release:plan` (`scripts/release/plan.mjs`, described in [[`docs/guides/releasing.md`](https://github.com/MapCairn/mapcairn/blob/main/docs/guides/releasing.md)](https://github.com/MapCairn/mapcairn/blob/main/docs/guides/releasing.md)) reads the reports' change since the last tag and the commits' types, and flags each change below as a likely breaking change. It cannot see everything above, so a person reads the go/no-go list in the Release pull request.

- a removed or changed line in a report, and a line that gained an `@internal` tag;
- a required member added to an exported interface or abstract class a host implements (an optional member, or a member of an ordinary class, does not count; for an abstract class only a new abstract member does). Hosts implement the ports, so adding a required member to one breaks them;
- an added or removed member of an exported union, or an added member of an enum. API Extractor may print a union on one line or on several, so the script reads the members from the report text itself. A union that loses members is reported as `union-member-removed`, likely breaking, and names them (the first 10, then the count of the rest and the total), and says what it gained;
- a change under `packages/core/src/urlHash/sharedLinks.test.ts` or `packages/core/src/layers/legacyDefinitions/` that removes or edits an entry (any removed line in the diff since the last tag). Adding an entry is not breaking.

The plan names removed and renamed message keys, because the keys are a union in the report (a rename shows as lost X and gained Y), but a person still writes them into the release notes and lists the new keys so a host can translate them. One kind of change no check sees needs a person: a stored format changed. While the version is `0.x`, a likely breaking change gives a minor bump; from `1.0.0` it gives a major one (the rules are in plan 0014).

## Who decides

The maintainer decides what is public: a new entry point, a change to the tag policy, a custom property or `data-*` name becoming public, and any breaking change. A contributor proposes it in the issue and the pull request; the pull request description names every breaking change and why. A reviewer who sees a change on this page without that note asks for it.

# The public API

What a host can rely on from the four SDK packages (`@mapcairn/core`, `@mapcairn/map`, `@mapcairn/react` and `@mapcairn/theme`), how a change to it is found in review, and how a change is classed for a release. The packages have been public since the `0.1.0-rc.1` release candidate (`docs/plans/0014-sdk-release.md`); this guide is the rule the release scripts and reviewers use.

## What counts as public

The public API is more than the TypeScript exports. A change to any item below is a change to the public API, and a change that makes it stop accepting or producing something it did before is a breaking change.

### Custom properties are not public; `data-*` style hooks are undecided

The maintainer has decided that the build-hashed custom property names (the token names in `tokens.css`, such as `--rogqo0r`) are **not public API**. They are private and may change in any release, so a host must not write a stylesheet against them, and a change to them is never a breaking change. Theming will go through a generated stylesheet, not through these names.

`data-testid` values are not public either (above). Whether the other `data-*` attributes the components set, which `styles.css` selects on, are public is still open: it is the maintainer's decision, listed among the open release decisions in #423. Until it is made, treat them as not public: a host should not write a stylesheet or a test against them, and a change to them is not a breaking change.

## What a tarball holds

`npm run pack:check` (`scripts/release/packCheck.mjs`) packs each SDK package with `npm pack --dry-run --json` and fails when a tarball holds anything but:

- `package.json`, `README.md` and `LICENSE`;
- files under `dist` ending in `.js`, `.js.map`, `.d.ts` or `.css`, which is all a build writes.

So no source (`src` is not in `files`; each `.js.map` carries its source in `sourcesContent`, so a debugger still shows it), no test or snapshot, no dotfile (such as `.env` or the `.built` stamp), and no data file, image, font or tile archive. It also fails when a file that `exports` or `types` names is missing from the tarball (the `@mapcairn/source` condition is left out, because it names a file only this repository has), when `files`, `publishConfig` or a `main` field differs from what the four manifests have, and when a tarball is over its size ceiling (`SIZE_CEILINGS` in the script, about one and a half times the size measured when it was set; raising one is an edit in a pull request). It also fails when `package.json`, `README.md` or `LICENSE` is missing, when `license` is not `AGPL-3.0-only`, when the fields the npm page shows are missing or wrong (`repository` with the package's own `directory`, `homepage`, `bugs`, `keywords` and `description`), and on a source map whose `sourceRoot` or a `sources` entry is absolute, a URL, or resolves outside the package's `src`. A script under `dist` must have a source map naming files that exist in `src`, except an entry point (named by `exports`) and the bundler's helper under `dist/_virtual`, and a declaration or stylesheet must be one an export names, so a stray file such as `dist/secret.js` fails. The check reads what is on disk, so the release `verify` job must run it after `npm run build:sdk -- --force` from a clean checkout, which empties `dist` first. It works on a private package, since `npm pack` does.

`npm run consumer:check` (`scripts/release/consumerCheck.mjs`) packs the four packages into a temporary folder outside the repository and installs them into a fresh app there, with the repository's `.npmrc` (so the seven-day minimum release age holds) and the versions of its six tools (`react`, `react-dom`, `vite`, `typescript` and the two `@types` packages) read from the root lockfile; the packages' own dependencies resolve fresh from the registry within the seven-day age. It installs with npm, with `--legacy-peer-deps` and, when one is already installed, with pnpm set to strict peer dependencies, and renders `MapChrome` in plain Node. In the npm install it then runs `tsc` under `bundler`, `node16` and `nodenext` resolution, builds with plain Vite (no plugins) that imports `@mapcairn/theme/tokens.css` and `@mapcairn/map/styles.css`, and renders the built server bundle. It also builds the app as a Worker with plain Vite, resolving with the `workerd`, `worker` and `browser` conditions, and runs that bundle on workerd (the Workers runtime the host is published on) through the Miniflare that the Cloudflare Vite plugin already installs for the repository. Those conditions choose the third-party builds a Worker takes, such as React's stream renderer; the packages' own exports have only the `@mapcairn/source`, `types` and `default` conditions, so what the leg shows is that their `default` build runs on Workers. The Worker reports its runtime name, so a render in Node cannot pass for it. workerd runs in a child process with a timeout that stops it on an interrupt, listens on 127.0.0.1 only (set explicitly) and sets no compatibility flag, so the packages need nothing beyond the plain Workers runtime. The Yarn leg installs the tarballs with Yarn Berry (the `node-modules` linker, no scripts, a seven-day minimum age) at the one exact version `YARN_VERSION` in `scripts/release/consumerLegs.mjs`, pinned in the app's `packageManager` with the sha512 digest corepack computes for that release (taken from a download into an empty corepack home, and checked there against a wrong digest, which corepack refuses) and fetched through corepack into its cache, which every project on the machine shares, then renders in plain Node and builds with plain Vite. The Bun leg installs with Bun (1.3 or later, the first to read the seven-day minimum release age; an older Bun fails the leg) and renders with it. It has never run: Bun was not available where it was written, so treat it as untested until someone runs it. It needs a network.

Some legs skip with a warning annotation on GitHub Actions when their tool is missing: pnpm (which is not installed for the check), Yarn when corepack is missing or cannot download Yarn (Node 25 and later ship no corepack), Bun only when `bun` is not on the path (any other Bun failure fails the check) and workerd when Miniflare is not installed, which is the case in a job that runs no `npm ci`. Nothing is installed for a skipped leg. The CI `SDK packages` job installs the repository's dependencies, so it runs the Yarn and workerd legs and skips Bun: installing Bun there would need a setup action that has not been pinned and reviewed. A job with no install, such as the release workflow's `check` job, skips the workerd leg; run `npm run consumer:check` on a machine that has Bun to cover Bun. The Yarn and Bun legs do not run against already published packages (`release:verify-published`), because their seven-day release age would refuse a release made today; they do run on packed tarballs, whether packed here or given with `--tarballs`, which are `file:` installs. The release workflow's `check` job runs the check on its tarballs with no `npm ci`, so there it runs the Yarn leg, skips workerd with a warning (no Miniflare) and skips Bun. Yarn Plug'n'Play is not checked: the check has not tried it, and Vite and Node would need Plug'n'Play-specific setup for it.

`map` lists `@vanilla-extract/css` in `dependencies` although nothing loads it at run time: `@vanilla-extract/recipes` names it as a peer, and a strict pnpm install (`strictPeerDependencies`, no automatic peers) refuses a missing one. The maintainer decided on 2026-11-20 to declare it as a dependency (about a dozen small permissively licensed packages) and not as a peer, which would put it on every consumer. Remove it if `recipes` drops the peer.

CI runs both in the `SDK packages` job, which is not a required check, and the weekly Repeatable build compares the `dist` folders and the tarballs of two clean builds.

The package READMEs are written for the npm page, which shows each one away from the repository. They install the package with npm, pnpm and yarn side by side, hold one **Status** line that says the packages are a release candidate (the `0.1.0` release changes it), and link to the repository only by absolute URL, because a relative link means nothing on npm. `packages/core/src/lint/packageReadmes.test.ts` checks this, and that the code in them imports only what `examples/embed` imports. The `repository.url` is `git+https://github.com/MapCairn/mapcairn.git`: npm's trusted publishing requires it to match the GitHub repository exactly, so a fork that publishes must change it.

## The report of the exports

Each entry point has a report, generated by API Extractor from its built declarations, at `packages/<name>/api/<entry>.api.md`:

- `packages/core/api/index.api.md` and `packages/core/api/contracts.api.md`
- `packages/map/api/index.api.md`
- `packages/react/api/index.api.md`
- `packages/theme/api/index.api.md`

The report lists every exported name with its signature, so a change to the public API shows as a diff in the pull request. The reports are generated, never written by hand.

- `npm run api:check` builds the SDK if it is stale, regenerates the reports and fails when one differs from the committed file, is missing, or has no entry point, printing the changed lines (at most 40). The CI step that runs it after the build is the gate. `packages/core/src/lint/apiReports.test.ts` also compares the reports during `npm test`, so a local test run finds the same failure, but it is not the gate and a skipped test run does not skip the check.
- `npm run api:update` regenerates and writes them. Run it after a change to an exported name, read the diff, and commit it with the change.
- Read the diff of a report as a reviewer would. A new line is a new export; check it was meant to be public. A removed or changed line is a breaking change, unless the member was never part of what a host used.
- A `// Warning: (ae-forgotten-export)` line means an exported declaration names a type the entry point does not export. A host can use the type but cannot import it by name. Export the type, or stop exposing it.

### Release tags

The maintainer has adopted this tag policy. Without a tag, every export in a report is public. The tags mean:

- `@public` (the default, so it is not written): covered by the rules on this page.
- `@beta`: exported so a host can try it; named in the release notes. Under `0.x` a minor release may break anything, so `@beta` is advisory until `1.0.0`. A host should not depend on a `@beta` export in a library of its own.
- `@internal`: in the entry point only because a barrel (`export *`) or another SDK package reaches it, and not supported: a tuning constant, an engine layer id or a helper that turns the SDK's data into engine input. An export that gains `@internal` is a likely breaking change (a host may use it today); one that is `@internal` from the start never breaks anyone. A name used only inside one package and its own file is not exported at all.

Without a tag an export is public. A light sweep of the four packages before `0.1.0` (see the export audit issue) hid the names that nothing outside their own file used and tagged the clearly internal ones `@internal`: pixel and timing constants, engine layer ids, and the helpers that build engine input in `map`. It is not an export-by-export audit: anything plausibly part of the supported surface stays public and untagged, and the rest of the review happens as the API evolves under the report check. A new tag appears in the report diff, which is how a reviewer sees that an export was narrowed. A name that a guide or a host's tests use stays public even when a sibling is tagged `@internal` (for example `MIN_SUGGEST_LENGTH` is public while `MIN_SEARCH_LENGTH` is `@internal`).

Two kinds of `ae-forgotten-export` warning remain, both in `core`. The `contracts` entry point names types that only the main entry exports (the rollup of `contracts` carries its own non-exported copies of them), and `MessageParams` names the unexported `MessageParamOverrides`. Neither stops a host from calling the API; the first needs a decision on how the `contracts` entry shares its types with the main entry.

### What produces the reports

The reports come from API Extractor, which reads the declarations with its own bundled TypeScript, while the build emits them with the repository's TypeScript 7. A new version of either can change every report, and the weekly dependency pull request that bumps them fails `api:check`. On that branch run `npm run api:update`, read the diff to see whether the change is real, and commit it. `.github/dependabot.yml` groups the two apart from the other npm updates, so this happens in one small pull request.

### TSDoc warnings

The same run prints warnings, and never fails on them:

- `ae-undocumented`: an export, or a member of an exported type, with no TSDoc comment.
- `ae-unresolved-link`: a `{@link}` that names something that is not exported.
- `tsdoc-*`: TSDoc syntax that API Extractor cannot read, such as an unescaped `}` or a `@param` with no hyphen.

CI prints each warning in a group and a count for each package as one annotation. The counts are not a baseline and nothing compares them with a limit. Whether to ratchet them is the maintainer's decision. `npm run api:check -- --verbose` lists every warning.

## Decisions on record

- **Tags.** The release tag policy above is adopted as written.
- **Export audit.** The maintainer decided on 2026-11-20 on a light sweep of the public exports before `0.1.0`, not a full audit (see the export audit issue). The first pass is described under Release tags.
- **Not public.** `data-testid` values (for the project's own tests, may change) and `peerDependencies` ranges (may change in a minor release while on `0.x`). The `data-*` hooks that `styles.css` selects on stay undecided.
- **Branch up to date.** Turning on the ruleset's "require branches to be up to date" is a maintainer step for later, once the release work settles. It is nothing for an agent to do; until then, two pull requests that both change a report can turn `build` red on `main` when the second merges.

- **Tool.** API Extractor produces the reports and the declaration rollup. TypeDoc is not used.
- **Published shape.** ESM only, with no `main` field. TypeScript resolves the packages with `node16`, `nodenext` or `bundler` resolution only, not `node10`.
- **Custom properties.** Not public (above).
- **Audit finding on `minimatch`.** `npm audit` reports a `minimatch` finding through `@microsoft/api-extractor`. It is accepted, with this record: API Extractor runs only at development and build time, never in a package a host installs, and the glob patterns it matches come from this repository's own build configuration, not from outside input. Drop the acceptance when API Extractor moves to `minimatch` 11 or later.

## How a change is classed for a release

`npm run release:plan` (`scripts/release/plan.mjs`, described in `docs/guides/releasing.md`) reads the reports' change since the last tag and the commits' types, and flags each change below as a likely breaking change. It cannot see everything above, so a person reads the go/no-go list in the Release pull request.

- a removed or changed line in a report, and a line that gained an `@internal` tag;
- a required member added to an exported interface or abstract class a host implements (an optional member, or a member of an ordinary class, does not count; for an abstract class only a new abstract member does). Hosts implement the ports, so adding a required member to one breaks them;
- an added member of an exported union or enum. API Extractor prints a short union on one line, so a new member shows as a changed line, and a long one on several lines; the script reads the members from the report text itself;
- a change under `packages/core/src/urlHash/sharedLinks.test.ts` or `packages/core/src/layers/legacyDefinitions/` that removes or edits an entry (any removed line in the diff since the last tag). Adding an entry is not breaking.

Two kinds of change need a person, because no check sees them: a message key removed or renamed (the release notes list new keys so a host can translate them), and a stored format changed. While the version is `0.x`, a likely breaking change gives a minor bump; from `1.0.0` it gives a major one (the rules are in plan 0014).

## Who decides

The maintainer decides what is public: a new entry point, a change to the tag policy, a custom property or `data-*` name becoming public, and any breaking change. A contributor proposes it in the issue and the pull request; the pull request description names every breaking change and why. A reviewer who sees a change on this page without that note asks for it.

# Repository reference

Detail behind [`AGENTS.md`](../../AGENTS.md): what each command does, the browser test setup, how the web host is built and deployed, and the issue and pull request process. `AGENTS.md` keeps the rules; this guide keeps the explanations they point to. Nothing here changes a rule.

## Commands in detail

- `dev` runs `cf dev`, which starts the Vite SSR dev server (`react-router dev`) on port 5173. It runs in Node, not in the Workers runtime, and never touches Cloudflare.
- `dev -w @mapcairn/docs` serves the documentation site on port 4410. `generate -w @mapcairn/docs` writes the generated theme stylesheet, the API reference pages (`sites/docs/docs/api`) and the pages built from `ARCHITECTURE.md` and `DESIGN.md` (`sites/docs/docs/generated`, with the sidebar entries in `_sidebar.json`), all git-ignored (`build`, `test` and `typecheck` run it first), and stops, naming them, when an export of an SDK package has no TSDoc summary or a package's committed API report is missing. `build -w @mapcairn/docs` builds it to `sites/docs/build` (CI's `build` job runs it as its own step; the root `build` does not, so a fault in the site's own build cannot stop the host's Workers Build; the docs build is still part of the required `build` check, and a broken lockfile entry stops both installs) and then runs `scripts/verifyBuild.ts`, which fails on a page in no sidebar, a link that goes nowhere, a style attribute, a resource from another origin, an inline script that is not on the committed list in `sites/docs/scripts/expectedInlineScripts.ts` (or one on it that is gone), a framework class the stylesheet targets that the pages no longer carry, a page with no Markdown copy, an `llms.txt`, `llms-full.txt` (which only lists the split files) or `llms-full-<area>` file that is missing or differs from what the pages give, an `llms.txt` over `LLMS_INDEX_CEILING` (150,000 bytes; `LLMS_FULL_CEILING`, also 150,000, is the most an `llms-full-<area>` file holds unless it is a single page; both in `sites/docs/scripts/markdownCopies.ts`), a copy with a code fence that has no language, a relative link or tabs, the copy of a part of `ARCHITECTURE.md` or `DESIGN.md` over `PART_CEILING` (40,000 bytes of Markdown, in `sites/docs/scripts/repositoryDocParts.ts`) plus `PART_COPY_ALLOWANCE` (2,000, in `markdownChecks.ts`), a `robots.txt` that blocks a crawler, a package with no API reference section, or a front page over the script budget (160,000 bytes of gzip script, plus 100 for each generated API page). `ARCHITECTURE.md` and `DESIGN.md` are too long for one page, so the generator cuts each by heading: an overview page at `/architecture/` or `/design/` (the address that held the whole document, so it still works) that lists every part with its size and the first sentence of its text, built from the headings and the text, and one page for each second-level section under it, such as `/design/tokens/`. A section over `PART_CEILING` is cut further, between blocks and between the rows of a table (each later part repeats the table header), into numbered parts, so `DESIGN.md`'s long components table is six pages today. The rule is the same every time and loses no text. A link to a heading, between the two documents or inside one, is rewritten to the page that holds it, and an old section anchor such as `/design/#tokens` still lands on that section's line in the overview, which links to its page (a redirect cannot do this: the Content-Security-Policy allows no inline script, and the framework's redirects drop the fragment); anchors on `###` and deeper headings are not kept. The generator refuses a document with text before its title or a code fence of more than three characters, and does not read an underlined heading as a heading. A single-file `vitest` run of a test that imports `sites/docs/sidebars.ts` needs `npm run generate -w @mapcairn/docs` first, because the sidebar reads the generated files. A `mermaid` block in a page is drawn at build time as inline SVG with a text alternative, by `sites/docs/plugins/remarkFlowchart.ts`: it reads top-down flowcharts with boxes, one level of `subgraph` and `-->` arrows, takes its colours from the site's tokens in both themes, and fails the build on any other Mermaid syntax or on a diagram wider than a phone's column (340 px laid out, `MAX_DIAGRAM_WIDTH`), so a diagram never scrolls sideways and the site needs no script or style for it. Stack the boxes and keep their text short. The source stays in the document, which GitHub draws itself. Its `cloudflare.config.ts` declares the second Worker, which owns `docs.mapcairn.com` as a Custom Domain. The first `cf deploy ./build` (which creates the Worker) and the Workers Builds project run only on the maintainer's own words in the session, as "Ask the maintainer first" says; the decision recorded on #199 records the choice and does not authorise the run, and an agent never runs the deploy script otherwise. Its tests are the Vitest project `@mapcairn/docs`, so `npm test` runs them.
- `build:sdk` builds `core`, `react`, `theme`, `map`, `adapter-maplibre` and `sdk` into `dist` (`ARCHITECTURE.md`, "Building the SDK packages"). The scripts that need `dist` run it first and it skips a package that is up to date, which means its sources, manifest and the build scripts (by content) have not changed since its last build. Run `npm run build:sdk` once before a single-file `vitest` run or a bare `playwright test`, which bypass those scripts.
- `test` runs Vitest across `packages/*`, `examples/*` and `sites/*`. Run one file with `npx --no-install vitest run path/to/file.test.ts`. It includes a check that fails on interface text written inline in `packages/map` or `packages/web` and on an Afrikaans value left as English (`DESIGN.md`, "What the lint checks, and where"); a new component looks its copy up through the message catalogue.
- `test:coverage` enforces 95% for statements, branches, functions and lines in `core`, `map`, `react`, `theme` and `adapter-maplibre`. `packages/web` has a slightly lower branch floor: 95% for statements, functions and lines and 90% for branches, because its layout and touch-gesture code is also covered by Playwright. Aim for 100% behavioural coverage.
- `test:mutation` runs Stryker (`stryker.config.mjs`) over the URL hash and measurement logic in `packages/core` and prints a mutation score: the share of small deliberate changes to the code that a test catches. A surviving mutant shows code a test runs but does not check. It takes about 20 seconds on a laptop and writes `reports/mutation` (git-ignored). The weekly `Mutation testing` workflow runs it, writes the score to the job summary and attaches the report; it only reports, is not a required check and never fails on a score. To widen the slice, add files to `mutate` in the config.
- `typecheck` checks every workspace, including web route types and the Playwright project, then the scripts (`typecheck:scripts`, `tsc -p scripts`): JSDoc types in `.mjs` and `.cjs` files, without `strict`.
- `lint` runs Biome, dependency-cruiser, the harmony scanner (`scripts/harmony`, see `DESIGN.md`), the licence header check (`scripts/licenceHeaders.mjs`), the SDK dependency licence check (`npm run licence:sdk`, see "Dependencies and lockfiles"), the agent files check (`npm run agents:check`), the roadmap check (`npm run roadmap:check`, see "Issues and pull requests"), the plans check (`npm run plans:check`, which only warns), the names check (`npm run names:check`, see "Boundaries"), the portability check (`npm run portability:check`, which fails on a home or drive path or a command that works on one system only in `scripts/`, the skills and agents, the instruction files and the guides), the moved guides check (`npm run guides:check`, which fails on a link or path to a guide that has moved from `docs/guides/` into the documentation site, `sites/docs/docs/guides/`), the prose check (`npm run prose:check`, which fails on a filler word from a short list, a second em dash in a paragraph, or more than eight bullets that start with a bold phrase in one page, in the documentation site's Markdown and the READMEs, and, in those and the root documents and `docs/guides`, on a logged decision or an ISO date; it prints the file and line), the release notes check (`npm run release:notes-check`, see `docs/guides/releasing.md`) and the publish guard (`npm run publish:guard`, which fails on a command that publishes to npm in a file that executes). Pre-commit runs every check except the roadmap check, the `commit-msg` hook runs the names check on the commit message, and neither runs typecheck, tests or coverage. The pre-push hook (`lefthook.yml`) runs `npm run typecheck` when the push changes a `.ts`, `.tsx`, `.mjs`, `.cjs` or `.json` file, and skips it for documents only; it takes about 7 seconds warm and 17 cold (build included). Lefthook does not run in a git worktree, so run `npm run typecheck` yourself before you push there.
- `build` builds every workspace. The web build runs `cf build`, which writes the Worker bundle and its static assets to `packages/web/.cloudflare/output`, then checks that this production output holds no browser test seam.
- `start` builds the e2e-mode bundle and serves it on port 4173 (or `MAPCAIRN_E2E_PORT`) with `vite preview`, which runs the built Worker in the Cloudflare Vite plugin's local runtime with the `e2e` settings from `packages/web/cloudflare.config.ts`. This build keeps the test seam, so it is not the production bundle. The `e2e` settings omit production routes, so the old-hostname redirect is not exercised. `cf` has no command that serves a build, which is why this one script calls Vite directly.
- `check` runs lint, typecheck, unit tests, build, e2e and a11y in sequence.

## Continuous integration

CI runs these workflows: `CI` (lint, typecheck, coverage, build, and the `SDK packages` check of the packed tarballs), `Playwright E2E` (the browser tests, split across four jobs, plus an advisory `docs browser checks` job for the documentation site), `Lighthouse CI` (the host, and an advisory `lighthouse docs` job), `CodeQL`, `CLA`, `Scorecard`, `Dependency review`, `Workflow security lint` (zizmor), `Secret scan` (TruffleHog), `Pull request title`, `Labeler` a weekly `Repeatable build` check and a weekly `Mutation testing` report (see `test:mutation` under "Commands in detail"). A pull request needs these checks to pass before it merges: `build`, `e2e`, `SDK packages`, `Dependency review`, `TruffleHog (pull request)` and `CLA` (ruleset `main-pull-requests`); the others are advisory. The `build` job also runs `scripts/apiBreakingCheck.mjs` on a pull request: when the API reports under `packages/*/api` show a likely breaking change (the classifier `npm run release:plan` uses) and the title has no `!` and the description no `BREAKING CHANGE:` footer, the job fails, with an error annotation and a job summary line that say what to do: mark the pull request as breaking (`!` in the title and a `BREAKING CHANGE:` footer) or revert the API change. It skips Dependabot and Release pull requests. The next step in that job runs `scripts/qualityBarCheck.mjs`, which reads `git diff -U0 origin/<base>...HEAD` (no network) and only warns, with an annotation on the file and line and a line in the job summary, each ending "say why in the pull request". It flags an added `biome-ignore`, `@ts-ignore`, `@ts-expect-error` or `eslint-disable` comment (except the `@ts-expect-error` above the import of a `.mjs` script, which every script test needs), an added `.skip`, `.todo`, `.fixme` or `.only` test, a deleted test file or test case (a removed `it(` or `test(` line with no added one in the file), a changed test file with fewer `expect(` calls than before, and a weaker bar in the files named in `BARS` in the script (the coverage thresholds in `vitest.config.ts`, the Lighthouse minimum scores, the size ceilings of the pack and consumer checks and the documentation site). A finding is a notice instead of a warning when the description has the words "quality bar" or names the file, so a "Quality bar" section is the way to explain one. The step skips Dependabot and Release pull requests and a run whose base branch cannot be read.

`Pull request title` fails a pull request whose title is not a Conventional Commit (`<type>[optional scope][!]: <description>`, with a type from `COMMIT_TYPES` in `scripts/prTitleCheck.mjs`), so the squash-merge subject is one the release scripts can read. Run it by hand with `PR_TITLE='fix(core): handle bounds' node scripts/prTitleCheck.mjs`. Its job, `Conventional Commit title`, could be added to the ruleset later; today it is advisory. `Labeler` adds area labels (`map`, `search`, `layers`, `design-system`, `a11y`, `performance`, `privacy`, `documentation`) from the paths a pull request changes, using the rules in `.github/labeler.yml`. It runs on `pull_request`, adds labels only and never removes one, and skips a pull request from a fork, whose token is read-only; a maintainer labels those by hand. `Stale` (`stale.yml`, the official `actions/stale`) runs weekly and only labels: an issue after 90 days and a pull request after 30 days without activity get a `stale` label (the action creates it) and one short comment, and nothing is ever closed. Issues labelled `plan`, issues with a milestone, anything assigned, and Release and Dependabot pull requests are exempt. `Pull request description` (`pr-body-check.yml`, logic in `scripts/prBodyCheck.mjs`) only warns, through an annotation and the job summary, when a description has no `Fixes #n` or `Part of #n` line or no `Checks` section; it never fails a pull request, and skips Dependabot and Release pull requests.

## Browser tests

```bash
npm run playwright:install -w @mapcairn/web
npm run e2e
npm run a11y
```

`e2e` runs every Playwright test except those tagged `@a11y`, and `a11y` runs only those. Playwright starts `npm run start` itself and reuses a server already running on that port (4173, or `MAPCAIRN_E2E_PORT`, which lets two checkouts run suites side by side). Page objects live in `packages/web/e2e/pages`, and shared helpers in `packages/web/e2e/support`. Locators use role and accessible name first, then `data-testid` (the configured `testIdAttribute`). The suite mocks basemap tiles, styles and Nominatim, so no test depends on a third-party service, and tests script geolocation, search, the clipboard, storage and the system theme through the test seam described in `ARCHITECTURE.md`.

Split repeated expensive work into separate cases before adding time. A case with a navigation or total timeout keeps it beside that case, explains why the work is inherently slow and does not change the global timeout or weaken an assertion.

The credits show themselves for five seconds after the map starts (while the first-visit tour is on screen the app holds them back and sets `data-intro-held`, and `collapseCredits` then returns at once with the credits still collapsed; a spec that answers the tour afterwards sees the credits show, and calls `collapseCredits` again to collapse them; the hold also ends on the first zoom or move of the map, or after `ATTRIBUTION_HOLD_MAX_MS`). A spec that only needs them out of the way sets the `fastCredits` option (`test.use({ fastCredits: true })`), which installs Playwright's clock before the page loads, and calls `collapseCredits` from `e2e/support/states.ts`, which jumps that clock past the intro. The first-showing tests in `attribution.spec.ts` leave the option off and wait out the real timer. A spec that would otherwise sleep past another app timer (a long press, the map settling, the scale bar's idle delay) installs the clock itself and steps past it with the values in `e2e/support/timers.ts`, which a unit test keeps equal to the app's constants.

Projects cover desktop Chromium, mobile Chromium (Pixel 7) and iPhone WebKit. WebKit runs only the basemap, keyboard, sheet and app-shell specs, because MapLibre worker startup and the bottom sheet can behave differently on iOS. Emulation cannot reproduce an iPhone GPU; basemap changes still need a real-device check. Two more projects, `rtl-chromium` and `rtl-mobile-chromium`, run those same four specs with `dir="rtl"` set on `<html>` (the `direction` option in `e2e/fixtures.ts`), in the app's own English: a pseudo-locale that proves the layout mirrors, not a shipped language. Three more pairs of projects (`expanded-*`, `mirrored-*` and `arabic-*`) run only `e2e/sample-languages.spec.ts`, once with each sample language in `e2e/support/language.ts` (accented English about 40 percent longer, right-to-left English, a small Arabic sample), through the test seam: collisions, cut-off text and the axe audit in every chrome state (see `sites/docs/docs/guides/translate-the-sdk.md`). A spec that depends on a physical direction reads `direction` from its fixtures, as the basemap arrow-key test does, because a radio group's arrow keys follow the reading direction.

## Web host and deployment

`packages/web/cloudflare.config.ts` declares the Worker: only the static `ASSETS` binding, routes and observability, with the production settings by default and an `e2e` mode for the local end-to-end server. `cf` (a beta, pinned exactly in `packages/web` and `sites/docs`) develops, builds and deploys it: `cf dev`, `cf build` and `cf deploy`, with `cf previews deploy` for a Preview. Run `cf` as `npx --no-install cf`; the project does not use Wrangler, and its bundler is the Cloudflare Vite plugin 2.0 (also pinned exactly). `cf build` accepts no `--mode` for this React Router project, so the e2e bundle is built with `react-router build --mode e2e`. For other Cloudflare work, use `cf` (the public API: zones, DNS, D1, KV, R2, logs and other resources; `cf cli search <words>` finds a command), and not a Cloudflare MCP server. It is the maintainer's tool to set up, so ask if it is missing. Production deploys still happen only by merging to `main`: Workers Builds runs `npm run build` then `npm run deploy` (the test-seam check, then `cf deploy --prebuilt --mode production`, which uploads exactly the output that was checked), and `npm run deploy:preview` (a production build, then `cf previews deploy`) for a Preview. Agents never run the deploy scripts. Deleting a remote resource still needs the maintainer. `workers/app.ts` forwards requests to React Router's server build, which the Vite plugin bundles into the Worker. The route table in `src/routes.ts` has the product page at `/`, the map (the playground) at `/map`, the privacy page, the `robots.txt`, `sitemap.xml`, `llms.txt`, `llms-full.txt` and `index.md` resource routes and `log-error`.
`entry.client.tsx` installs client error reporting before hydration. React Router's request handler, server rendering and the Worker wrapper log server errors; the root error boundary logs and reports an error in the browser, once per error. `routes/log-error.ts` validates bounded client reports and logs them without a database.

The inline theme bootstrap in `root.tsx` (source in `src/app/themeBootstrap.ts`) prevents a flash before hydration. The product page also has two fixed inline scripts, `src/app/mapLinkRedirect.ts` and `src/app/copyCodeScript.ts`, and runs no framework script (`src/app/scriptlessPage.ts`). If the source of any of them, or the offered languages and directions the theme script embeds, change, recompute its exact SHA-256 CSP hash in `public/_headers` and `src/constants/securityHeaders.ts`. Keep font and app CSS as module imports so the build emits the font files. The metric-matched fallback face comes from `@mapcairn/theme`'s `tokens.css`, not from the host.

Production CSP permits no `unsafe-inline` script or stylesheet source. New basemap or geocoder origins must be allowed in `public/_headers`; local development does not apply those headers. The MapLibre worker must stay compatible with iOS and the production CSP.

## Issues and pull requests

Work is tracked in GitHub Issues, and an issue is enough for most of it: put the design notes and the task list in the issue. Write a plan in `docs/plans/` only for a large change that crosses several packages or decides a public API, where the design needs review before code; every plan has a tracking issue linked from its file. Give that review its own pull request, ahead of any code, only when the work will not start straight away, such as a change the maintainer wants to weigh before committing resources, or one several people will build over time. When the work starts immediately, write the plan file and its first implementation in one pull request instead: the plan still lands in `docs/plans/` and still needs every section `plan-change` lists, but there is no separate, idle review pass waiting on it before the code that builds it. Anyone can open an issue. Whoever takes the work, a contributor, the maintainer or an agent, keeps it current: label it (`map`, `search`, `layers`, `design-system`, `a11y`, `performance`, `privacy`, `plan`, `documentation`, plus `bug` or `enhancement`), put it in a GitHub milestone (the one that fits, or "Maintenance" for quality, process and test-stability work), tick its task list as steps land, and close it when the work is merged and verified. Create an issue for any new piece of work worth tracking. Do not file an issue for a gap that can be fixed in the same session; fix it. `ROADMAP.md` ranks milestones, not issues ("Priorities": Now at most three, Next at most six, Later milestones only): an issue is listed nowhere in it. A new issue takes a milestone when one fits; only a new milestone is proposed for the roadmap, ranked last in its section, and a finished milestone is removed in the pull request that closes its last issue. The order is the maintainer's call, so an implementer reports any other change as an issue to file, and `npm run roadmap:check` (part of `lint`) reports a linked milestone or issue that is missing or repeated and a section over its cap, and warns about a closed one or a "Last reviewed" date more than 60 days old; `npm run plans:check` warns about a plan whose tracking issue is closed; the pull request that finishes a plan's last step deletes it. Issues are public, so write plain project facts only, never emails, keys or private details. The skills in `.claude/skills/` carry out this process with the `gh` CLI: `shape-work` (business analysis: the problem, the people, acceptance criteria and ranked issues), `design-solution` (solution options, a decision record and a design review), `design-ux` (flows, states and copy before the code), `create-issue`, `plan-change`, `split-plan`, `pick-up-issue`, `land-pr`, `visual-check`, `review-ui` (reading interface code against `DESIGN.md`), `review-docs` (checking documents against the code and each other), `review-security` (a change checked for security and privacy risk), `review-layer` (a layer or provider checked for terms, privacy and failure behaviour), `web-platform-guidance` (looking up the current native HTML, CSS and browser API answer before writing interface code), `playwright-tests` (writing and healing browser tests), `design-tests` (what to test at which level, before the code), `review-tests` (breaking the code on purpose to see whether a test fails), `triage-production` (reading the deployed site's health with `cf` and `curl`, read-only), `adopter-check` (following the published packages and the public guides as an outside developer, and reporting where a guide fails), `triage-dependency-pr` (taking a dependency pull request to a green merge) and `release` (preparing a Release pull request for the SDK packages, never publishing; `docs/guides/releasing.md`). The agents `implementer`, `fresh-eyes-reviewer`, `ui-verifier`, `architecture-reviewer`, `ux-reviewer`, `test-reviewer` and `security-reviewer` in `.claude/agents/` wrap them. They are the source for the copies other tools read (`.agents/skills`, which holds the project's own skills, `.agents/agents`, `.opencode/agents`, `.codex/agents`, `.github/agents`, `.qwen/agents`), which `npm run agents:sync` writes and `npm run lint` checks: edit the source, then sync.

# Design system

The map is the hero and the chrome recedes. MapCairn is calm, neutral and precise, with grouped controls, a floating search pill and a bottom sheet, in the way people already expect from a good maps app. Light and dark are equally polished. The target is WCAG 2.2 AA, built in from the first component.

Tokens live in `packages/theme/src/tokens.css.ts`. Components may only use tokens, so an off-scale value fails typecheck, and a lint test is the backstop for raw literals.

### How the CSS ships

The SDK ships compiled CSS, not `.css.ts` source, so an app that uses it needs no vanilla-extract plugin. `@mapcairn/theme` ships `tokens.css`, which holds every token's `:root` block and its dark-theme blocks once, and `@mapcairn/map` ships `styles.css`, the styles of every component. An app imports both, `tokens.css` first:

```ts
import "@mapcairn/theme/tokens.css";
import "@mapcairn/map/styles.css";
```

The packages' JavaScript imports no CSS, so server rendering (Workers included) loads plain modules and the stylesheets are static assets that a strict Content Security Policy allows: nothing is inlined. In `theme`'s manifest `sideEffects` names only `.css` files; `core` and `react` set it to `false`; `map` names `**/*.css` and `**/*.css.ts`. A bundler therefore keeps the stylesheet imports and drops unused JavaScript. The `.css.ts` pattern is for a host that resolves the source condition, as `packages/web` does, and does nothing for an app that uses `dist`. `styles.css` holds the styles of every component, whether or not the app uses it. The primitives' styles sit in one cascade layer, so an app's own unlayered rules beat them, element resets included; put the app's base styles in an `@layer` declared before `styles.css` is imported ("Overriding a primitive").

`map` is built against the built `theme`, never its source, so the custom property names in `styles.css` are the ones in `tokens.css`; a test in `packages/core/src/lint/sdkDist.test.ts` fails if `styles.css` reads a property that neither file defines, unless it is a readable name (two or more lower-case words, such as `--sheet-offset`) that a component sets from JavaScript, or if `styles.css` repeats a token property. A generated name must always be defined in a stylesheet. A repository build tool resolves the `@mapcairn/source` condition instead and compiles the source itself, as `packages/web` does.

`@mapcairn/adapter-maplibre` ships a third stylesheet, `styles.css`, which holds the rules that fit MapLibre into the map region (hide its controls, take its type and background from the tokens). `MapLibreMapAdapter.ts` imports `styles.css.ts` so the build compiles it, its `sideEffects` list is the same as `map`'s, and it uses the same custom property names as `tokens.css`, which `sdkDist.test.ts` checks. Its built JavaScript imports no stylesheet of its own; it loads the engine's own stylesheet dynamically, beside the engine, the first time a map mounts. `packages/web` resolves the package's source and so does not import this stylesheet.

The token custom properties have generated names (`--rogqo0r`, say), which stay the same for a given build of the packages and may change between releases. A stylesheet written by hand should not name them. The maintainer has decided they are not public API: they are private and may change in any release, and theming goes through a generated stylesheet, not through these names (`createThemeStylesheet`, under Tokens; `sites/docs/docs/guides/public-api.md`). An app reads token values through `tokens` from `@mapcairn/theme`, as `examples/embed` does for its page colours.

The generated class names in `styles.css` (such as `._1n4n9ad2`) are not API and may change in any release. `styles.css` also holds a few selectors that are not scoped to a generated class. `[data-tour-highlight="true"]` matches any element on the page with that attribute, and rules such as `[data-layout="sheet"] > <class>`, `[data-dragging="true"] <class>`, `[data-minimised="true"] > <class>` and `[data-disabled="true"] > <class>` match when any ancestor carries the attribute, as does `* + <class>` for a sibling. The `data-*` attributes the components set (`data-layout`, `data-detent`, `data-state` and the rest) are used by those rules and by tests; whether a host may rely on them is not decided.

A host restyles the SDK through `createThemeStylesheet` (colours for each theme, `fontFamily` and `shape`, for each scope), and the generated property names stay private. The SDK ships no base stylesheet and no alias properties, and the host provides its own base styles and a cascade layer for its reset, declared first. A base stylesheet, alias properties, per-component styling hooks, density, slot moves, icon swaps and a light or dark choice for one map alone are out until a named adopter needs one. See "What an app of your own provides" in [Extending MapCairn](https://mapcairn.timothybrits.co.za/docs/guides/extending/) and the task [Theme the interface](https://mapcairn.timothybrits.co.za/docs/tasks/theme-the-interface/).

## Living style guide

A developer page in the reference host that draws every token and primitive from the real code.

`/design` renders every token and every primitive from the real code: colour roles with light and dark hex values and their contrast pairs, the type scale, spacing, radii, elevation, motion, z layers, the Phosphor icons the app imports, each component in each state, and a font check that proves IBM Plex Sans is rendering. Open http://localhost:5173/design with `npm run dev`, or http://localhost:4173/design with `npm start` (the e2e build). The route exists only in development and in the `--mode e2e` build (`packages/web/src/designGuideRoutes.ts`), together with `/design/host-theme/:name`, which serves two generated host themes for the browser tests; `npm run build` fails if the page's marker reaches the production bundle, and `e2e/design.spec.ts` and `e2e/theme-override.spec.ts` cover it in the browser.

## Principles

The rules every part of the interface follows.

1. One of everything: one family, one accent, one icon set, one weight, one radius per role. Syntax highlighting in code samples is the one documented exception to the accent rule (see "Syntax palette").
2. Every control has one owner of its position (`MapChrome`) and one layer (a named z-index).
3. Nothing is conveyed by colour alone.
4. Nothing needs a gesture, a hover or a mouse. Every gesture has a keyboard or single-tap equivalent.

## Tokens

The colours, type, spacing and other values the interface is built from.

- **Colour roles:** surface, surface-raised, text, text-muted, accent, accent-tint, hairline, danger, scrim, focus-ring, page-background, map-background, map-globe-space. The neutral ramp is OKLCH with a faint cool tint. The accent is one clear blue. Page-background follows the theme and sits behind full pages such as the privacy policy. Map-background is the land colour of the theme's default basemap, Bright's in the light theme and Fiord's in the dark theme, so the map region before the map draws matches the map that follows for a visitor who has not chosen another basemap. A visitor who chose one sees that colour only until it draws. Map-globe-space is the space around the sphere when the map is a globe, and only then: a cool mid grey in the light theme (`oklch(0.82 0.02 250)`), dark enough that pale land at the edge of the globe still shows and light enough to sit with the light chrome, and a dark blue in the dark theme (`oklch(0.31 0.025 255)`), dark against the dark chrome yet lighter and bluer than the near-black Dark basemap, so its edge shows too. A test keeps it at 1.2:1 or more against the land of every built-in basemap, and the chrome text over it at 4.5:1.
- **Basemap:** the default basemap follows the theme until the visitor chooses one: Bright in the light theme, Fiord in the dark theme, so dark controls sit over a dark map on a first visit. A basemap the visitor has chosen never changes by itself: it stays across theme changes and reloads, and pressing the tile that is already shown counts as choosing it. A visitor who never chose follows the theme live, so switching the theme switches the map. Nothing is saved until a choice, so an old saved "auto" or a removed id is no choice. A shared link names the basemap that was showing, so the same link shows the same map to everyone, whatever their theme; a link with no basemap, such as one typed by hand, shows the viewer's own default. Links made before this rule named Bright, so they still open on Bright in either theme. A reload keeps the basemap the address names, so a visitor who never chose and reloads in the other theme sees the map the address names, not their theme's default; the next theme change drops it and following resumes. The picker offers what the host supplies. The reference host offers six, in this order: Bright (the light theme's default), Liberty, Positron, Streets, Fiord and Dark, as manual choices like any other. They sit in a grid of three columns: Bright, Liberty and Positron on the first row, and Streets, Fiord and Dark on the second. The SDK defines seven (`BASEMAPS`): the six the host offers, and Colorful, which a host may offer. The reference host builds its own catalogue from a subset of the SDK's list, to ask fewer volunteer-run servers for tiles and to keep the picker short. The reference site once offered Topographic and Satellite; both were removed, Topographic because its provider is volunteer-run with no availability guarantee, and Satellite because its imagery is licensed for non-commercial use only. A saved or linked id the host does not offer (`colorful`, the removed `satellite` or `topographic`, the old "auto", or the retired `maptoolkit-dark`) shows the default for the viewer's theme, and a saved value is left alone. Dark is OpenFreeMap's neutral dark style, and it asks for no more than the credit text the other OpenFreeMap styles carry. Fiord is OpenFreeMap's blue-toned dark style, the default in the dark theme, and asks for the same credit text. Its land colour, `#45516e`, is a mid-dark blue-grey that is neither contrast extreme, so it is a backdrop of its own in the contrast tests. All of the interface is checked over it in both themes, because light chrome over Fiord happens when a visitor picks it in the light theme, and dark chrome over Bright when they pick Bright in the dark theme. A tile with no `swatch` of its own shows the light default's land colour in either theme, wherever it shows a plain swatch (no preview image, or a preview that failed to load). In the SDK, Colorful is VersaTiles' style, from a provider other than OpenFreeMap, which carries its credit text (OpenStreetMap contributors, VersaTiles, ESA WorldCover 2021 and the CC BY 4.0 licence it is under) and nothing else; its land colour is the default's, so it needs no swatch. A basemap with no preview image, or whose preview image fails to load, shows a plain swatch. The SDK's definitions name no preview at all, so a host that serves none shows a swatch for each of them; the reference host adds previews for the six it offers (`BASEMAP_THUMBNAILS` in `packages/web/src/basemaps/basemapThumbnails.ts`). A definition may set `swatch`, a hex colour for that tile, so a dark basemap does not look like the pale default: Dark's and Fiord's are their styles' own land colours. The picker applies it with a custom property set through CSSOM, never an inline `style` attribute. On it, the selected tile's check badge stays legible in both themes (the tick on the accent disc, and the disc or its raised-surface ring against the swatch, at least 3:1), and the name sits below the tile on the sheet. The SDK carries no provider whose licence it would have to accept; a host adds one as data (see `ARCHITECTURE.md`, host-supplied basemaps).
- **Map overlays:** the pin, the measure line, the vertices and handles of drawn shapes and the accuracy circle draw in the theme's overlay colours: accent-600 with a white halo in the light theme, accent-400 with the near-black surface halo in the dark theme. The pin, every line and the accuracy outline are drawn on a halo (a wider stroke of the halo colour beneath them). Over a basemap each shows when the mark or its halo reaches 3:1 against the land and the mark reaches 3:1 against its halo, which the token tests check over white, black, a light map, Bright and Fiord in both themes. Only a role the map draws on a halo gets that credit in the tests; a mark drawn without one must reach 3:1 against the map itself. A saved image always uses the light theme's colours, because its white halo shows on every basemap, and its credits strip is white with dark text on any of them. Data layers draw with the data palette, whose dark edge and white halo carry them over any basemap.
- **Data palette:** the one set of colours data layers draw with, separate from the interface roles. Seven Okabe-Ito categorical colours (without black) and a five-step ordered ramp, light to dark, in `tokenValues.dataPalette`. Definitions name a slot (`vermillion`, `ordinal-3`), never a value; categories must use categorical slots and steps ordinal ones. Every marker has a dark edge inside a white halo (`tokenValues.dataMarker`), the same on the map and in the legend, so the pale steps show on a light map and the dark ones on a dark surface; contrast tests cover both. Validation refuses a colour rule with no shape, size or words beside it.
- **Syntax palette:** the colours of highlighted code on the documentation site, in `tokenValues.syntaxPalette` for each theme. It is the one exception to the one-accent rule, for code only: the interface, the map and every other page keep one accent. Nine roles, each its own muted hue so a reader tells them apart without the accent alone: keyword (purple), string (green), number (rust), function (the accent blue), class name (teal), property (gold), and comment, punctuation and operator from the neutral ramp, with comments italic and lower in emphasis than punctuation. The background is not a role: a code block sits on `surfaceRaised` over the page background, and a highlighted line on `accentTint` over that (`--docusaurus-highlighted-code-line-bg`), so nothing here adds a surface colour. Added hues have chroma 0.12 or less. `sites/docs/scripts/syntaxCss.ts` writes each role as `--mc-syntax-<role>` (generated, git-ignored), and `custom.css` maps the highlighter's token classes onto them. `syntaxPalette.test.ts` holds every role to 4.5:1 on the code block and on a highlighted line in the default, opaque and `prefers-contrast: more` colour sets, in both themes, and requires five or more hues. - **Surfaces:** translucent with backdrop blur, at most a tenth of the map showing through (the surface colour is 92 percent opaque in both themes), so place names under a panel cannot be read through its text, with an opaque fallback and the `-webkit-` prefix. `prefers-contrast: more` and `prefers-reduced-transparency` make them opaque and remove blur. Contrast is computed over the worst-case backdrops (pure white and pure black map) and over the land colour of both default basemaps, Bright's and Fiord's, because either theme can sit over either map once a visitor chooses one, and Fiord's mid-tone is the worst case for some colours.
- **Checking a host's colours:** `checkThemeContrast(override)` in `@mapcairn/theme` takes a partial override of 14 interface roles (`surface`, `surfaceRaised`, `text`, `textMuted`, `accent`, `accentTint`, `accentContrast`, `hairline`, `controlBoundary`, `danger`, `dangerTint`, `scrim`, `focusRing`, `focusRingInner`) for light and dark. A role left out keeps its default. It returns data, never throws and never decides whether a theme is accepted: one finding for each pair, theme and backdrop (the ratio, the minimum, the backdrop and whether it passes), plus a list of colours it could not check (unparseable, an `oklch()` colour outside the sRGB gamut, translucent where the role must be opaque, not an overridable role, or an object that throws when read). The parser reads numbers and percentages strictly and clamps out-of-range components as CSS does; it refuses keywords such as `none`, empty or extra arguments, a slash or comma in the wrong place and angle units other than degrees. Only hex, `rgb()`/`rgba()` and `oklch()` are supported; named colours, `hsl()`, `oklab()` and `color()` are reported as unparseable. An override that is not a plain object, a section that is not, or a key that is not part of the shape is reported too, never passed. The minimums are WCAG 2.2 AA: 4.5:1 for text, 3:1 for control edges, the focus ring and its inner ring; hairlines and the scrim are exempt. Translucent surfaces are flattened over white, black, a light map and the land colour of each theme's default basemap (Bright's and Fiord's). On the bare map the focus ring is judged by its better tone: it passes when the outer or the inner tone reaches 3:1. Muted text is held to 4.5:1 and the control edge to 3:1 on the accent tint, as a selected list row and a switch hover draw them. Text, muted text and the accent are also held to 4.5:1 on the page background, and text to 4.5:1 on the map halo; those two backgrounds are not overridable, so they stay at their defaults. Only the default colour set is checked. The pair table is internal (`packages/theme/src/contrastPairs.ts`), shared with the token tests in `contrast.test.ts`. The function only checks; `createThemeStylesheet` below applies an override.
- **Applying a host's colours:** `createThemeStylesheet(override, { scope })` in `@mapcairn/theme` turns the same override into a stylesheet, or refuses. A theme below WCAG 2.2 AA is refused: the result has `ok: false`, no CSS and the findings (and the colours or scope it could not use), so a host fixes its colours first. A theme that passes returns `ok: true`, the CSS and the findings. The host serves the CSS as a same-origin file and links it after `tokens.css` and `styles.css`, so it needs no inline style, no nonce and shows no flash. The scope is the selector of an element the host owns around the SDK's interface (`:root`, `#id` or `.class`, ASCII only; anything else is refused), and the SDK adds no markup or attribute for it. Two scopes are two calls and two independent stylesheets. The rules read `data-theme` on the root element, or the operating system's colour scheme when there is none, in four contexts that never overlap, so a role set for light only does not show in dark. Every rule is inside `(not (prefers-contrast: more))` and `(not (forced-colors: active))`, so in high-contrast and forced-colours modes the SDK's own values apply. Each colour is parsed with the strict reader above and written back as `#rrggbb` or `#rrggbbaa`, and the check runs on the written values, so no other text reaches the stylesheet. Where the surface is translucent the generator also writes an opaque surface, the surface flattened over the theme's page background, for browsers without `backdrop-filter` and for `prefers-reduced-transparency`, and sets the inner focus ring to it unless the host chose one; both are checked too. The page background, the map overlay roles and the data palette cannot be overridden, and neither can anything but colour, the font family and the corner preset. `fontFamily` is a closed list of plain family names, quoted or not, and generic families, so no brace, semicolon, `url()`, `var()`, comment or newline reaches the sheet; it is written once for the scope, outside the high-contrast conditions, with the SDK's stack after it as the fallback, through the same private name as the typeface token. The host loads the font file, from its own origin or an origin its `font-src` allows. A font's width cannot be known when the stylesheet is made, so the layout is tested instead: `packages/web/e2e/theme-font.spec.ts` puts a deliberately wide face on the chrome at 320 and 390 px in both themes and checks that no control gets smaller than it is with the SDK's font and that nothing overlaps; text in a control may be cut short. The tooltip, which renders in a portal, copies the font family from its trigger as it does the colours. The custom property names are build hashes the generator reads from `tokens`; they match the SDK's stylesheet only when both come from the same installed `@mapcairn/theme`, and they are not public. A tooltip renders in a portal under `body`, outside the host's scope, so it copies the colour properties its trigger sees onto the bubble when it opens (`inheritTheme`, through the style object, which the strict policy allows); the host does nothing for it, and it is the only component that renders in a portal. A portal added later must do the same. The steps for a host are in [Theme the SDK with your own colours](https://mapcairn.timothybrits.co.za/docs/guides/extending/#theme-the-sdk-with-your-own-colours).
- **Spacing:** 4, 8, 12, 16, 24, 32. Screen inset is 12.
- **Radii:** pill 24, sheet 20, control and card 14, inner 10. Fully circular elements use 50%. A host can choose a `square` or `round` preset with `shape` in `createThemeStylesheet`, which sets those four radii for its scope: square is 4, 4, 2 and 2; round is 24 (still a pill, half the 48px search row), 28, 22 and 16, so no radius reaches past half a control's 44px minimum height. The circular role is never changed. `packages/web/e2e/theme-shape.spec.ts` walks every chrome state at phone, tablet and desktop sizes in both themes for each preset and checks that nothing overlaps, no control gets smaller and no corner cuts text, an icon, a field or a focus ring; the tooltip copies the radii from its trigger like the colours.
- **Elevation:** two shadows, floating and sheet, each with light and dark values. No borders on floating elements. Hairlines only inside lists and between grouped controls.
- **Type:** IBM Plex Sans only, self-hosted through Fontsource (variable, Latin and Latin Extended), weights 400 and 600. Sizes 13, 15, 17 and 22, defined in rem with a line height and tracking each, and one display size, 40 (`type.display`), for the heading of a full page that is not the map (the product page's h1, which scales between the title and display sizes with the viewport); the map's chrome never uses it. Code samples, and nothing else, use `type.familyMono`, the system's own monospaced faces, so no second web font is downloaded. Nothing below 13px. Numbers use `tabular-nums`. Inputs are 17px, never below 16px. The stack puts a metric-matched fallback face, `IBM Plex Sans Fallback`, right after Plex. It has no font file: a `local()` face over Arial or Liberation Sans with `size-adjust` and metric overrides derived from Plex's metrics, so the swap to Plex moves the layout very little. It is declared once, in `packages/theme/src/tokens.css.ts`, so `@mapcairn/theme/tokens.css` ships it to every app and the host declares none of its own; `tokens.css.test.ts` checks that the face and the stack name the same family. The rest of the fallback stack is `system-ui, -apple-system, "Segoe UI", Roboto, sans-serif`, which also covers non-Latin place names. The scale is script-aware: tracking is negative on the large, title and display steps and line heights are tight, which suit Latin text and break Arabic joining and Indic conjuncts. Text whose `lang` is in `tokenValues.nonLatinLanguages` (Arabic-script, Hebrew, Indic, Thai, Lao, Khmer, Burmese, Amharic, Georgian, Armenian, Japanese, Korean and Chinese) reads the `type.nonLatin` tokens instead: tracking `0em` (small's 0.01em is zeroed too, since any letter spacing breaks joining) and a line height of 1.6 on small, body and large and 1.5 on title and display, applied by one `:lang()` rule that sets the variables on the element carrying the language. Latin output is unchanged, except that custom properties inherit, so a Latin span inside a listed language keeps the looser values, which is harmless. The list is not exhaustive and a host adds rules for others. The SDK ships no non-Latin font; a host sets `type.family` (and, if it wants other values, `type.nonLatin`) under its own `:lang()` rule, as `sites/docs/docs/guides/translate-the-sdk.md` shows, and the theme's rule never sets `type.family`.
- **Size:** controls are 48px minimum, targets never below 44px, switches and slider thumbs included (their hit area is larger than what they draw), with at least 8px between neighbours.
- **Icons:** `@phosphor-icons/react` only, imported by name, 24px, one weight (regular, and fill for a solid heart), through the `Icon` component.
- **Focus ring:** two tones (an inner surface ring and an outer ring, 2px each) so it shows on any basemap. Every interactive element and the focused map use it. In the dark theme the outer tone is accent-400, light enough to show on Fiord's mid-dark land, where the inner tone, the dark surface colour, shows over a white map.
- **Right to left:** styles use logical properties only (`marginInlineStart`, `paddingInlineEnd`, `insetInlineStart`, `borderStartStartRadius`, `textAlign: "start"`), never `left`, `right` or their `margin`, `padding` and `border` forms, and the harmony scanner fails a physical one (`logical-property`). Layout that has to move sideways with a transform (a slide, a switch thumb, a scale bar) sets it again in the same rule under `[dir="rtl"]` with the sign reversed; the scanner accepts a horizontal translation, a gradient direction or a transform origin only when its rule has a `[dir="rtl"]` selector. Use the attribute selector, not `:dir(rtl)`: the build rewrites `:dir()` into a list of languages, which does not match English text on a right-to-left page. The device safe-area insets are physical (`env(safe-area-inset-left)`), so `safeArea` in `packages/map/src/chrome/safeArea.ts` gives the `ltr` pair and the `rtl` pair, set under `[dir="rtl"]`. The tokens hold no direction. A host that ships a right-to-left language sets `dir="rtl"` on `<html>` (with `lang`), and nothing else in the SDK needs to change; `useReadingDirection` in `@mapcairn/react` reads it for the Radix slider and segmented control and for map fitting, and the chrome measures its offsets from the inline-start side. Icons that point along the reading direction, such as a back arrow, a next or previous chevron and undo and redo, mirror: pass `mirrorInRtl` to `Icon`, `Button` or `IconButton`. Icons that do not, such as a magnifier, a pin, a clock or a vertical chevron, do not. A map direction (the arrow keys panning the map, the compass) stays physical. Text that is not catalogue copy is isolated so it keeps its own order inside right-to-left text: components wrap place names, addresses, feature titles, the scale label, distances and areas, and coordinates in `Isolate` (`figure` for the ASCII coordinates). A message's own parameters (a coordinate in "Pin dropped at {position}", a layer name in a sentence, each item of a list) are wrapped by `createMessageCatalogue` in Unicode first-strong isolates (U+2068 to U+2069) when its language reads right to left, or when the host passes `isolateParameters: true`; a left-to-right catalogue returns plain strings. The marks are invisible, so a host's tests strip U+2066 to U+2069 from text before an exact-name assertion; a translator writes the same `{name}` placeholders as before, and no message carries markup. No right-to-left language ships on the reference site, but a host can offer one; the `rtl-chromium` and `rtl-mobile-chromium` Playwright projects keep the layout honest (see `AGENTS.md`).
- **Motion:** 120, 200 and 320ms, one easing curve, one spring for the sheet. Only transform and opacity animate. `prefers-reduced-motion` turns motion off, including MapLibre's own animation.
- **Z layers, bottom to top:** map, mapOverlay, chrome, chromeRaised, sheet, toolbar, popover, toast. Components name a layer and never write a number. The tokens file and the map engine style file are the only places raw z-index values may appear.

## Layout and slots

Where each control sits on the screen, and which part of the code owns its place.

`MapChrome` owns the position of everything floating over the map. It is `pointer-events: none`, and each slot's contents are `pointer-events: auto`. The cursor coordinates remain on screen while a pointer rests over the readout after it grows, so the coordinates can be copied; they clear after the pointer leaves both the map and the readout.

The side panel sits at inline-start: on the right in a right-to-left layout. Feature reveals, imported shapes, directions and free-centre targets use the measured panel edge on that side; route, shape and layer-feature fits also keep the end-stack clearance on inline-end, and layer-feature fits stay above the visible map key.

Before the app mounts, the server renders a decorative skeleton of this chrome (`ChromeSkeleton`) on the map's background colour: the search pill, the Map options, Measure, Directions (when the host has a routing service, which `ChromeSkeleton` is told with its `directions` prop), Draw shapes (its `draw` prop), Locate me and Settings group, the zoom group where the device has a fine pointer, and the credits button, in their final slots. It reuses the `MapChrome` grid and the real controls' own classes, so the live chrome replaces it in the same boxes with no layout shift (`e2e/skeleton.spec.ts` compares every control's box before and after at 390 by 844 and 1280 by 720). It is `aria-hidden` and `inert`, writes no `style` attribute and uses only tokens. It uses no hook or provider, so its words arrive as a required `copy` prop, built from the host's default-language catalogue by `chromeSkeletonCopy` with the keys the live controls use. Because the server cannot measure the container, its sheet or side panel layout follows a media query built from the same constants as `chooseLayout`, and its zoom group follows `(hover: hover) and (pointer: fine)`; a stored "show zoom buttons" choice is applied once the app mounts. Where scripts do not run (`@media (scripting: none)`), nothing would ever bring the controls to life, so the placeholder draws neither the skeleton nor its loading text and the skip link is hidden; `NoScriptNotice` shows instead, a card in the middle of the placeholder, inside the main landmark so it is not empty, that says "The map needs JavaScript. You can still read about MapCairn, its source code and its privacy policy." with links to the product page, the source and the privacy policy. The server renders it in English, because without scripts the page cannot read the visitor's stored language.

Slots use flow layout with gaps from the spacing scale, so neighbours push apart instead of overlapping. On narrow screens the sheet is a bottom sheet with peek, half and full detents. From 768px wide, and on any screen shorter than about 500px, it is a floating side panel at inline-start. The bottom slots ride above the sheet and hide at the full detent. They clear only what is in the bottom-centre slot (the toolbars, toasts, the connection notice and the tile-error banner), so a host puts its own toolbar there, and each slot rides above it by that slot's own height only when the two share width (within a gap), in the same frame the slot changes height: a control moves only when a surface that opens would cover it, and then by the least that clears it, and otherwise holds still. A centred toolbar on a tablet or desktop therefore leaves the credits at the end of the row and the readout at the start where they rest, and on a phone, where the toolbar spans the row, both rise. `MapChrome` measures each slot's horizontal extent as it will rest (counting the sideways shift of the side panel), and writes `--chrome-bottom-start-raise` (the readout), `--chrome-map-key-raise` (the map key, which rests above the readout but can be wider than it, so it has its own span and rises to clear a toolbar that reaches it alone) and `--chrome-bottom-end-raise` (the credits) in the callback of the observer that sees the slot change size, and the slots apply them with the `translate` property, which no transition covers, while the sheet's lift (`--chrome-bottom-lift`) is a `transform` that slides with the sheet. A toolbar that changes height (opening, a first measure, a larger text size) therefore never has the credits or the readout over it for a frame, with motion or with reduced motion, and `e2e/toolbarLift.spec.ts` records every frame to check it. The credits button holds still where the toolbar shares no width with it, but its open popover is wider than the button and can reach under a toolbar or message that the button does not, so `MapChrome` also writes `--chrome-popover-centre-rise` in that same callback, from the popover's own box (also when it opens or moves beside the end stack), and the popover applies it with `translate`: it is clear of the slot in the frame the slot appears and never slides over it, while its rise over the readout, a `transform`, still slides. The tour card, which sits at the top of the free space, gives way to a toolbar that shares its width and reaches up to it. `MapChrome` measures the bottom row, so the credits popover rises above its tallest slot (unless it shares no width with the readout, see the bottom-end row) and its height is capped at the room between that row and the end stack (`--chrome-bottom-end-rise`, `--chrome-bottom-end-room`); a slot added to the row, or a readout that grows, therefore cannot overlap the popover. The end stack is capped at the height `MapChrome` measures for it and scrolls inside that height on a screen too short for every control, with no scrollbar. It is a scroll container only while it has more to show (`data-scroll-more` is not `none`): with every control in view it does not clip, because a clip would cut the groups' shadows at its box and leave a hard-edged band that dims the map beside the controls on the dark theme. Text size counts as screen size: controls and the search pill are in rem, so at 200 percent text (WCAG 2.2 1.4.4) or 320 px wide (1.4.10) every control must still be reachable, by scrolling where it cannot fit, and never cut off with no way to reach it. The one residual: on a 320 by 568 screen at 200 percent text with the draw tool open, the end stack's window is about 120 px against 96 px buttons, so the second button shows only in part, inside the fade band, until it is scrolled to. A scroll container with a hidden scrollbar says it has more by fading the edge that has more behind it (`scrollFade`, driven by `data-scroll-more` from `useScrollEdges`: `below`, `above`, `both` or `none`), a control brought into view by Tab stops clear of the fade, and a fade is a mask, so it takes no room and is removed in forced colours (`forced-colors: active`). The draw toolbar takes at most half the screen height, and less where the end stack would be left without room for one button (its cap is the screen height minus what the rest of the chrome needs, in the same rem units, so it follows the text size); beyond the cap it scrolls inside its surface the same way, and the shape switch wraps onto a second line instead of its words overlapping. The primary button does not stick: the surface is translucent, so a pinned row would show the scrolled controls through it, and at large text the button row wraps to several lines, which would pin most of the toolbar. The browser test `text-size.spec.ts` checks 100, 150 and 200 percent text at 320 by 568, 390 by 844 and 820 by 1180, in English and Afrikaans. By default the zoom group yields to a short stack. When the user has chosen to show zoom buttons it stays, and scrolls into view with the rest of the stack. `e2e/bottomCorners.spec.ts` records the box of the credits, the readout and the map key at a phone, a tablet and a desktop size before and after each tool opens, and fails a control that moves when nothing would cover it, or that does not clear what would. A layout collision test checks every viewport and state, including, on a desktop pointer, the readout with the cursor coordinates at their widest, imperial units and a key of six layers, from 320 by 568 up.

Map options and Settings open the same sheet or side panel, each at its own sections, so the sheet shows either the Map options group or the Settings group, never both. Settings is always the last button of the main group. Each button is an expanded toggle (`aria-expanded`, `aria-controls` the sheet) that is true only while its own group is the open surface (a pin card in the sheet counts for neither). Pressing a button while the other group is open switches to its group without closing the sheet, and pressing it while its own group is open closes the sheet. Closing returns focus to the button that opened the open group (Map options or Settings), or to the Shapes button of a drawing the sheet was opened over. Shapes and export, a tap on a feature and a dropped pin's card all land on the Map options group, whichever group was open. A sheet opened over Measure or Draw returns to that tool when it closes, with its points or shape kept and focus on the Measure button or the Shapes button.

### Overriding a primitive

The primitives that take a `className` (`Surface`, `Button`, `IconButton`, `Chip` and the `ListRow` body) define their styles with `primitiveRecipe` (`packages/map/src/ui/primitiveRecipe.ts`), which puts every rule of the recipe, with its selectors and media queries, in one cascade layer (`primitives`, declared in `primitives.css.ts`). A style outside any layer beats a layered one whatever its specificity or the order the stylesheets load in, so a component restyles a primitive with a plain class passed as `className`: a background, a radius, a shadow, a border colour. Never double a selector (`&&`) to win, and never rely on the stylesheet order. A new primitive that takes a `className` uses `primitiveRecipe`; a recipe that is a component's own style (such as `StatusMessage`'s) stays a plain `recipe`.

What the layer changes:

- A component's plain rule also beats the recipe's state rules (hover, active, focus, pressed). A component that sets its own background therefore sets its own hover and focus styles, as the credits button does.
- Unlayered rules beat the primitives, in this repository and in an adopter's app. The host's default focus outline (`:where(:focus-visible)`, in `packages/web/src/global.css.ts`) outranks the recipes' own outline, so the two keep the same `outline` and `outlineOffset` (both come from `focusRing`; a test pins them). Do not add an unlayered rule for `button` or another element a primitive renders unless it is meant to win.
- Known trade-off for adopters, decided on 2026-11-20 for 0.1.0: an unlayered element rule in an app (`button { background: transparent; border: 0; padding: 0 }`, say, or `:focus-visible { outline: none }`) now beats every primitive whatever its specificity or the stylesheet order. Before the layer, the primitive's class beat an element selector. An app's base styles and resets therefore go in an `@layer` that is declared before `@mapcairn/map/styles.css` is imported, because a layer declared earlier ranks lower, so the primitives outrank it. The layer name stays generated and private, so an app cannot order it by name. This is revisited if an adopter reports a problem.
- The built `styles.css` uses one layer with a generated name. Each file that holds primitive rules repeats the one-line statement `@layer <name>;` before its blocks, so the name is declared several times, in the middle of the file and not first; with one layer the repeats change nothing, and the first sits ahead of every block that uses it. `npm run consumer:check` builds a throwaway app with a layered reset imported before `styles.css` and checks a primitive keeps its background, padding and border.
- Forced colours and `prefers-contrast: more` still apply: they come from the tokens, which are not layered, and from the same layered rules.

`e2e/primitive-override.spec.ts` moves the recipe's rules to a stylesheet added last and checks the credits button keeps its surface, radius and shadow (its hover case passes without the layer and only guards the hover rule); `packages/core/src/lint/sdkDist.test.ts` checks the built `styles.css` and that every primitive recipe uses `primitiveRecipe`.

## Exempt surfaces

The few places that may hold raw values instead of tokens.

These surfaces hold raw values on purpose and are exempt from the harmony lint (`npm run lint:harmony`, `scripts/harmony`):

- the tokens file (`packages/theme/src/tokens.css.ts`, `tokenValues.ts` and the contrast code and tests)
- the map engine style file (`packages/adapter-maplibre/src/styles.css.ts`), the only place MapLibre selectors (`.maplibregl-*`) and raw engine z-index values may appear
- basemap definitions (`packages/core/src/basemaps`): committed basemap assets and map style definitions are data, and carry their own colours, such as a picker swatch
- the documentation site (`sites/docs`), which the scanner does not read (it walks `packages` and `examples`). Its stylesheet is generated from the exported tokens (`scripts/themeCss.ts`), and `themeCss.test.ts` and `customCss.test.ts` hold it to token references, with no colour literal and no `!important`. Its syntax colours are values in the tokens file (`tokenValues.syntaxPalette`), generated into custom properties, so the stylesheet still holds none
- tests, fixtures and test support
- `node_modules` and build output

Text baked into basemap tiles comes from the tile source and keeps its own typeface. The inline theme script in `packages/web/src/root.tsx` is a string, so no rule reads it. The scanner's header and `scripts/harmony/config.mjs` list the same surfaces.

One other list exists. `scripts/harmony/allowlist.mjs` holds one-off, justified exceptions (rule, file, snippet and reason), and a stale entry fails the lint. The one entry for the `logical-property` rule covers the loading bar's keyframes, which cannot carry a `:dir(rtl)` selector, so the sweep is written twice.

Biome restricts a fixed list of browser APIs, not every global:

- **Outside `packages/core/src`:** `noRestrictedGlobals` denies the bare `localStorage`, `sessionStorage`, `matchMedia`, `fetch`, `location` and `history`. `noJsRestrictedProperties` denies those six as properties of `window`, `globalThis` or `self`, and also `navigator.geolocation`, `navigator.clipboard` and `document.location`.

- **In `packages/core/src`:** a wider deny replaces them: every property of `window`, `document`, `navigator`, `self` and `globalThis`, the six bare globals above, and the bare `window`, `document`, `navigator`, `self`, `requestAnimationFrame`, `cancelAnimationFrame`, `XMLHttpRequest`, `WebSocket`, `indexedDB`, `HTMLElement`, `Element`, `Node` and `Event`.
